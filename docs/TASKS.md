## P0 · 공정성·버그

### T-01 3개 블록 순차 배치 가능성 검증

**배경.** 디자인 원칙 "공정한 긴장": 게임오버는 운이 아니라 플레이어 선택의 결과로 느껴져야 합니다. 현재 `BlockData.get_adaptive_trio()`의 "Solvability Check"(`scripts/block_data.gd:362`)는 세 조각이 모두 `all_fitting`에서 뽑히므로 항상 통과하고, 실제로는 아무것도 검증하지 않습니다. "각 조각이 지금 보드에 놓일 수 있다"와 "세 조각을 어떤 순서로든 모두 놓을 수 있다"는 다릅니다.

**작업 내용**
- `Board`에 그리드 상태를 복사하는 함수(예: `get_occupancy_snapshot() -> Array`, 8×8 bool)를 추가합니다.
- 스냅샷 위에서 동작하는 순수 함수를 만듭니다: 배치 가능 위치 열거, 배치 적용, 줄 클리어 적용.
- 3개 조각의 순열 6가지 × 각 단계의 모든 배치 위치를 깊이 우선으로 탐색하고, 하나라도 끝까지 가면 즉시 `true`를 반환합니다. 줄 클리어를 반드시 반영합니다(앞 조각이 줄을 지워야 뒤 조각이 들어가는 경우).
- 검증에 실패하면 세트를 다시 뽑습니다(최대 N회, 예: 8회). 그래도 실패하면 해결사(도미노·작은 코너)로 한 슬롯씩 교체하며 재검증합니다.
- 기존의 무의미한 검증 루프는 제거합니다.

**성능 주의.** Web 빌드(GDScript, 싱글 스레드)라 최악의 경우 64³×6 탐색이 될 수 있습니다.
- 첫 성공에서 바로 종료합니다.
- 점유율이 낮을 때(예: 40% 미만)는 검증을 생략합니다.
- 탐색 노드 수 상한을 두고, 상한을 넘으면 "검증 실패"로 처리해 재추첨합니다.
- 목표: 세트 생성 1회당 웹에서 체감 지연 없음(대략 10ms 이내).

**관련 파일**: `scripts/block_data.gd`, `scripts/board.gd`

**완료 기준**
- [ ] 무작위 보드 1,000개 이상에 대해 "해결 가능한 세트가 존재하는데 해결 불가능한 세트를 지급하는" 경우가 0건 (에디터용 테스트 씬 또는 스크립트로 확인)
- [ ] 점유율 70% 이상 보드에서 세트 생성 평균 시간을 측정해 기록
- [ ] 기존 슬롯 역할(해결사·라인 완성·압박)과 순서 섞기가 유지됨
- [ ] Web 빌드에서 세트 지급 시 끊김 없음

### T-04 플레이 이벤트 로그 수집

**배경.** 기획서 13장의 지표(판 길이, 즉시 재시작률, 최대 콤보, 위기 구간 체류, 게임오버 원인, 부활 수락률, 재방문)를 보려면 이벤트가 필요합니다. 지금은 게임오버 때 점수만 보냅니다.

**작업 내용**
- 클라이언트: 이벤트를 메모리에 모았다가 게임오버·앱 이탈 시 한 번에 전송하는 모듈을 만듭니다(새 Autoload 또는 `LeaderboardManager` 확장).
- 이벤트 정의(초안):

| 이벤트 | 필드 |
|---|---|
| `session_start` | user_id, 시각, 플랫폼 |
| `game_start` | game_id, 재시작 여부, 직전 게임오버로부터 경과 초 |
| `tray_dealt` | 블록 ID 3개, 점유율, 위기 여부 |
| `place` | 블록 ID, 칸 수, 지운 줄 수, 콤보, 남은 유예, 배치 후 점유율 |
| `revive_offer` / `revive_result` | 수락 여부, 제거 칸 수 |
| `game_over` | 점수, 플레이 시간, 배치 수, 최대 콤보, 마지막 세트 블록 ID, 점유율, 부활 사용 여부 |

- 서버: `POST /api/block-game/events`를 추가하고 날짜별 JSONL 파일에 append 합니다. 요청 크기 제한을 둡니다.
- 설정 또는 첫 실행 안내에 수집 사실을 짧게 표시합니다.

**관련 파일**: `scripts/main.gd`, `scripts/leaderboard_manager.gd`(또는 신규), `tools/server_block_leaderboard.js`

**완료 기준**

### T-07 오늘의 챌린지 (날짜 시드 + 일간 랭킹)

**배경.** 모두가 같은 조건에서 겨루는 공정한 비교와, 매일 돌아올 이유를 줍니다.

**먼저 정할 것.** 현재 생성기는 보드 상태를 보고 블록을 고르기 때문에(적응형), 시드가 같아도 플레이어마다 블록이 달라집니다. 아래 중 하나를 정해야 합니다.
- **A. 고정 순서**: 챌린지 모드에서는 시드로 미리 만든 블록 순서를 모두에게 똑같이 지급(적응형 끔). 공정하지만 막히는 판이 생길 수 있음.
- **B. 시드 + 적응형**: 같은 시드로 시작하되 적응형 유지. 덜 공정하지만 체감 난이도는 일반 모드와 같음.
- 권장: **A**. "같은 문제를 누가 더 잘 푸나"가 챌린지의 핵심이기 때문입니다.

**작업 내용**
- `BlockData`가 전역 `randf()/randi()` 대신 주입된 `RandomNumberGenerator`를 쓰도록 바꿉니다(일반 모드는 무작위 시드).
- 챌린지 시드: 날짜(KST) 기반 정수.
- 서버: 랭킹에 `type=daily` 추가(날짜 키별 최고 점수).
- UI: 홈 화면에 "오늘의 챌린지" 버튼, 랭킹 모달에 "오늘" 탭. 하루 도전 횟수 제한 여부 결정.

**관련 파일**: `scripts/block_data.gd`, `scripts/main.gd`, `scripts/leaderboard_manager.gd`, `scripts/leaderboard_modal.gd`, `scenes/main.tscn`, `scenes/leaderboard_modal.tscn`, `tools/server_block_leaderboard.js`

**완료 기준**
- [ ] 같은 날 두 기기에서 챌린지를 시작하면 첫 세트가 동일 (A안 기준)
- [ ] 일간 랭킹이 날짜가 바뀌면 초기화
- [ ] 일반 모드 동작은 변하지 않음
